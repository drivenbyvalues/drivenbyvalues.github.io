# Parsec — A Self-Service PaaS Portal for a Multi-Petabyte Data Platform

*Year shipped: 2020 · Platform area: Platform Engineering · Status: production*

## Why It Existed

At a Fortune-500 payments network's internal data platform organization, the core Hadoop analytics cluster grew from roughly 20-40 PB of storage and under 15,000 vCores of compute in early 2018 to 100-150 PB and 60,000-90,000+ vCores by mid-2020 — active users climbing from several hundred to several thousand over the same window. None of the operational tooling around that cluster scaled with it. Cluster and queue visibility was generated by hand, on request, for a workload running roughly 15,000-25,000 jobs a day. A small team spent its time just keeping the infrastructure security-patched. Onboarding a new engineer onto the Hadoop/Spark/analytics stack took a couple of weeks of manual directory-group and edge-node setup. Storage quotas existed for HDFS but not for the parallel GPFS filesystem, and the HDFS NameNode itself was under strain from tens of thousands of top-level directories and hundreds of millions of files. Expanding the cluster meant a lengthy, multi-step manual checklist per node, and dataset usage/audit reports took a few weeks to produce by hand against tens of gigabytes of logs.

On top of that, every new "as-a-service" idea on the data platform — a Kafka service, a database service, a data-transfer service — was at risk of reinventing its own UI and control plane instead of building on shared infrastructure.

I led the design and delivery of Parsec, the self-service PaaS portal that became the answer to all of it — and, as it grew, the operating layer underneath every other platform service on the data platform.

## What It Does

Parsec started life as "Platform Portal" and was renamed as its scope grew from a single Hadoop admin tool into a general **PaaS Controller Framework**: a shared layer of resource orchestration (compute/storage/network provisioning) and service orchestration (lifecycle, configuration, monitoring, scaling, security policy) that any underlying "platform" — Hadoop, Kafka, Spark, DB2, and eventually Kubernetes — could plug into by implementing a small set of hooks, rather than building its own automation stack from scratch.

In production, that meant:

- A central **Workflow Executor Service** issuing commands over REST to a **PaaS Agent** running on every managed host — agents poll for work, execute it, and push results back through a transient, per-execution file-transfer channel.
- An **Inventory Manager** acting as the single source of truth for every host's identity, configuration, and installed packages across the fleet.
- A catalog of self-service apps — user onboarding, storage/queue management, package management, workflow automation, job analysis, agent management — built on the same shared plumbing, with Kafka-as-a-Service as one of the first tenant apps hosted on the framework.
- An **App Builder Framework** that let adjacent teams (a data-transfer service, a database-as-a-service, a Spark-as-a-service) build and host their own front ends on Parsec's UI shell and data model instead of standing up separate portals — with WCAG 2.1 AA accessibility compliance built in as a platform-level guarantee rather than something each team had to re-solve.

## Key Decisions

- **Pull-based agent polling over REST**, not a push model. Agents check in for work rather than being pushed to — simpler to build and secure at fleet scale, at the cost of latency we later worked to close with a websocket-based push model.
- **An ephemeral, per-execution file-transfer service** for command output instead of a persistent, load-balanced file service — the agent talks directly to an `ip:port` the workflow executor hands it for that one execution, avoiding the need for a domain name or load balancer on that path, at the cost of keeping a port range open on every host.
- **A shared App Builder Framework instead of per-team portals.** Every new PaaS offering built its UI on Parsec's framework rather than its own stack. That consolidated UI cost and let us enforce accessibility and design standards centrally, at the cost of coupling those teams to Parsec's release cadence.
- **Moving off commercial automation tooling** (Chef, Puppet, Ansible Tower) as the security posture matured — a zero-trust policy eventually prohibited automated SSH access outright, so we built a self-developed shell/Go agent framework instead of depending on tools that assumed SSH.
- **HashiCorp Vault for secrets** rather than a custom credential store, cutting secret-retrieval time from days down toward roughly one day.
- **Formal reliability-tier certification and internal "Tool" registration** — a deliberate move from treating Parsec as a departmental utility to running and certifying it like any other production platform, complete with defined recovery-time and recovery-point targets.

## Why This Matters

Parsec is the clearest example in my career of an internal tool graduating into a platform. It started as a way to stop hand-running Hadoop admin tasks and ended up as the deployment, provisioning, and identity backbone for an entire generation of "as-a-service" products — Kafka-as-a-Service, a database-as-a-service, a data-transfer service, and eventually Spark-on-Kubernetes — all reusing the same portal, the same agent fleet, and the same accessibility and security baseline instead of each reinventing it.

By its third full year in production, Parsec was running on 7,000-11,000+ agents across the fleet, fronting 1,200-1,800+ API endpoints, and had cut new-hire onboarding time by roughly 300-500x and dataset-usage-reporting time by roughly 600-1,000x compared to the fully manual process it replaced — onboarding that once took a couple of weeks fell to a day or two. None of that came from one clever feature. It came from consistently choosing the boring, reusable infrastructure primitive — a shared agent protocol, a shared portal shell, a shared secrets store — over letting each team build its own one-off version.

## Tech Stack

- **Runtime** — Node.js app tier plus a dedicated Node.js workflow/file-transfer tier
- **Agents** — a self-developed shell/Go agent framework running on every managed host
- **Secrets** — HashiCorp Vault
- **Config/automation** — Ansible-based workflow automation, RPM package distribution
- **CI/CD** — Jenkins pipelines
- **Data** — MySQL (regional master/slave with cross-region replication)
- **UI** — a Material UI–based React front end, built to WCAG 2.1 AA
- **Comms** — REST polling evolving toward WebSockets for near-real-time task execution
